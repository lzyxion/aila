## 결정과 이유

- **실행 한도 초과는 422 거절이 아니라 clamp + 경고 코드** (`range_clamped`, `limit_clamped` 등). "지난 24시간" 요청이 정책 한도에 걸려 튕기는 것보다 한도만큼 보여주는 편이 낫고, 조정 사실은 `query_runs.warnings` 에 코드로 남는다. 반대로 정책 **저장** 시점의 한도 값은 clamp 하지 않고 422 — 저장은 사람이 고칠 수 있는 순간이라 조용히 바꾸면 설정이 실제와 달라진다.
- **`openai_compatible` 은 OpenAI 어댑터로 매핑, base_url 필수** (`llm_providers/factory.py`). enum 에 값이 있는데 팩토리가 거부하는 충돌의 해소. vLLM 등 호환 엔드포인트를 별도 어댑터 없이 지원.
- **정책의 `default_range_minutes` 는 기본값이자 실행 상한을 겸한다.** "기본 1시간, 최대 6시간"이 필요해지면 전용 컬럼 + 새 revision.
- **BackgroundTasks 는 요청 세션을 쓰지 않는다** — FastAPI 0.106+ 는 yield 의존성을 백그라운드 태스크보다 먼저 정리한다. 태스크는 engine 만 물려받아 새 세션을 연다 (`analysis/service.py`).
- **멱등은 코드 체크가 아니라 DB 제약** — `analysis_jobs(fingerprint) WHERE status IN ('pending','running')` 부분 유니크 인덱스(revision 0002) + IntegrityError → 기존 작업 반환. 체크→삽입 코드는 동시 요청에 반드시 뚫린다.
- **LLM 응답 검증은 어댑터 밖 한 곳** (`parse_analysis_result`). 어댑터는 원시 dict + 토큰 수만 반환. strict 스키마 변환에서 제거된 값 제약도 같은 지점이 강제한다.
- **llm-mock 을 인프라에 포함** — 요청의 json_schema 로 응답을 생성하고 `/debug/last-request` 로 수신 페이로드를 노출. API 키 없이 E2E 가 돌고, "LLM 요청 페이로드에 원문 비밀값이 없음" 단언이 실제 전송 경로에서 성립한다.

| 심각도 | 결함 | 수정 |

| med | Python 트레이스백 "상위 프레임"이 반대(진입점) 프레임 | 형식별 분기, 정규화 v2 |

## Phase 4 — 1차 사용 피드백 (백엔드 몫)

- **모델 목록 조회는 어댑터 인스턴스가 아니라 classmethod** (`OpenAIProvider.list_models` / `AnthropicProvider.list_models`). 모델을 *고르기 전에* 필요한 조회라 `model` 이 필수인 생성자를 태울 수 없다. `LLMProvider` ABC 의 연산은 `test_connection`·`analyze` 둘뿐이라는 어댑터 계약은 그대로 뒀다 — 목록 조회는 인스턴스 연산이 아니라 엔드포인트 조회다. 프로바이더 분기는 `factory.list_models` 한 곳(=`build_llm_provider_from_values` 와 같은 지원 판정·`openai_compatible` base_url 필수 규칙)에 모았다.
- **`POST /api/llm-connections/models` — 조회지만 GET 이 아니다.** 처음에는 `api_key` 를 쿼리스트링으로 받는 GET 이었는데, 그러면 평문 키가 서버 액세스 로그·프록시 로그·브라우저 히스토리에 남는다. **비밀을 실어 보내는 요청은 조회여도 바디로 받는다** (`LLMModelListRequest`). GET 라우트는 남기지 않았다 — 하위 호환을 위해 유출 경로를 살려 두면 그 경로로만 계속 호출된다.
- **`/models` 는 `/{connection_id}` 보다 위에 등록한다.** 아래로 내려가면 `"models"` 가 경로 파라미터로 먹혀 422 가 난다. 실패는 프로바이더 사유면 502, 입력 오류면 400 이고 `detail` 은 마스킹을 거친다(평문 키·base_url 내장 자격증명 유출 차단). 프론트는 실패 시 자유 입력으로 폴백하므로 `detail` 에 **원인**을 남기는 것이 계약의 핵심이다.
- **`provider` 는 바디에서도 열거형이 아니라 `str` 로 받는다.** 모르는 이름을 pydantic 이 422 로 튕기면 프론트의 `isEndpointMissing` 이 "경로 없음"으로 오해해 원인 없이 폴백이 켜진다. 라우터에서 **사유가 담긴 400** 으로 바꾼다. (바디로 옮기면서 `connection_id=` 빈 값을 정수로 파싱해 주던 헬퍼는 사라졌다 — JSON 은 `null`·생략으로 "지정 안 함"을 표현한다.)
- **실행 이력 목록의 정렬은 `started_at DESC, id DESC`.** `started_at` 만으로는 같은 초에 들어간 두 건의 순서가 흔들려 페이지 경계에서 행이 중복되거나 사라진다. `group_count` 는 페이지 행에 대해 **한 번의 group-by** 로 센다(행마다 count 쿼리 금지).
- **일일 한도의 "하루" 는 UTC 자정 → `app_settings.timezone` 의 로컬 자정.** UTC 기준이면 한국에서는 업무 시작 시각인 오전 9 시에 카운터가 리셋돼 "어제 저녁에 쓴 분량이 아침까지 남는다". 로컬 자정을 먼저 구하고 UTC 로 변환하는 **순서**가 핵심이다(반대로 하면 9 시간 어긋난다). 타임존은 쓰기 시점에 `zoneinfo` 로 실제 로드해 검증한다 — 오타를 받아 두면 비용 차단 장치가 판정 시점에 조용히 멈춘다. 읽기 경로도 로드 실패 시 기본값으로 내려간다(예외로 분석이 막히지도, 무제한이 되지도 않게).
- **revision 0003 은 데이터 전용**(스키마 변경 없음): `timezone` 행 시드 + `daily_analysis_limit` 설명 문구 갱신. 저장된 description 이 in-code 문구보다 우선하므로, 0002 를 이미 돌린 DB 는 이 revision 없이는 "UTC 자정 기준" 을 계속 보여 준다.
- **(프론트) 분석 이력 무한 로딩의 원인은 캐시 무효화 부재였다.** 작업 폴링(`useAnalysisJob`)은 작업 캐시만 갱신하고, 이력은 그룹 상세(`error-groups/{id}`)의 `analyses` 에서 온다 — 작업이 끝나도 그룹 캐시를 무효화하는 경로가 없어 스피너만 남았다. 수정은 폴링이 종료 상태로 바뀌는 지점에서 **한 번만** 관련 캐시 3종을 무효화 (`useAnalysisJobWithRefresh`).
- **(프론트) mock 은 실제 백엔드와 같은 응답 봉투를 유지한다.** `/usage` 백지 버그의 원인이 정확히 이것이었다 — 백엔드는 `{total, items}` 봉투를 주는데 mock 이 배열을 줘서, mock 에서만 동작하는 화면이 라이브에서 죽었다. mock 의 역할은 편의가 아니라 **계약 회귀 검증**이다.
- **(프론트) 소스에 리터럴 제어 문자를 넣지 않는다.** `'\0manual'` 리터럴 NUL 바이트 하나 때문에 ripgrep 이 파일 전체를 바이너리로 취급해 조사에서 통째로 누락됐다. 같은 의미면 `'(U+0000)manual'` 이스케이프로 쓴다.

## Phase 5 — 인증 · 스케줄러 · 통합 대시보드

- **세션은 무상태 서명 토큰이 아니라 DB 행이다** (`user_sessions`). 요구가 "만료 + **로그아웃 무효화**" 둘이었는데, HMAC 서명 토큰은 만료만 지킨다 — 서버가 아무 상태도 갖지 않으므로 "로그아웃했다"를 표현할 방법이 없고, 쿠키 삭제는 브라우저 쪽 정리라 이미 유출된 토큰은 남은 12 시간 동안 그대로 유효하다. 사용자별 epoch 를 두는 변형은 "이 세션만 끊기"를 표현하지 못한다. 비용은 요청당 유니크 인덱스 조회 1 회다. 쿠키에는 임의 256 bit 토큰을 싣고 DB 에는 **SHA-256 해시만** 저장한다 — 복호화가 필요 없는 값이라 Fernet 을 쓰지 않았고, 테이블을 읽어도 유효한 쿠키를 만들 수 없는 편이 낫다.
- **비밀번호 해시는 stdlib `hashlib.scrypt`, 저장 형식에 파라미터를 담는다** (`scrypt$n$r$p$salt$hash`). 새 의존성(passlib·bcrypt·argon2)을 넣지 않는다는 제약에서 출발했지만, 파라미터를 값 안에 적는 선택은 그와 별개다 — 나중에 비용을 올려도 **기존 행이 그대로 검증된다.** 형식을 코드 상수에 묶어 두면 비용을 올리는 순간 전 계정이 로그인 불능이 된다. `verify_password` 는 깨진 행에 예외 대신 `False` 를 준다: 로그인 경로가 500 을 내면 인증이 없는 것보다 나쁜 상태(아무도 못 들어가고 원인도 안 보임)가 된다.
- **보호는 라우터별 `Depends` 가 아니라 앱 전역 의존성 한 곳이다.** 라우터마다 붙이는 방식은 기본값이 "열림"이라, 새 라우터를 추가하면서 한 줄 빼먹으면 조용히 뚫린다. 전역 의존성 + 경로 화이트리스트(`PUBLIC_API_PATHS = {login, logout}`)로 기본값을 "닫힘"으로 뒤집었다. 미들웨어가 아니라 의존성인 이유는 두 가지다 — 요청 세션(`get_db`)을 그대로 물려받고, `HTTPException` 을 타므로 401/403 의 `{detail}` 형식이 나머지 오류와 같아진다.
- **`/api/auth/me` 는 인증 예외에 넣지 않았다.** 미인증이면 401 이 나와야 프런트가 `/login` 으로 보낼 판단을 할 수 있다. 예외로 두고 `{"user": null}` 을 주면 401 인터셉터가 무의미해진다.
- **로그인 실패는 사유를 구분해 주지 않는다.** "그런 계정 없음"과 "비밀번호 틀림"을 나누면 계정 이름 열거가 된다. 계정이 없을 때도 더미 해시를 한 번 태워 응답 시간 차이를 줄인다.
- **관리자 시드는 마이그레이션이 아니라 앱 기동 시점이다.** 마이그레이션에서 비밀번호를 시드하면 그 revision 을 돌린 모든 DB 에 데모 기본값이 박힌다. 그리고 **이미 계정이 있으면 아무것도 하지 않는다** — 재기동마다 env 값으로 되돌리면 운영자가 바꾼 비밀번호가 매번 사라진다. 시드 실패는 기동을 막지 않는다(마이그레이션은 사람이 통제한다는 규칙 때문에, 스키마 적용 전 기동이 정상 경로에 있다).
- **기존 테스트 430 개는 conftest 의 기본 admin 세션으로 통과시켰다** — 대체 지점은 `auth.dependencies.identity_from_request` 하나다. `dependency_overrides` 로 하면 각자 `create_app()` 을 부르는 테스트 모듈 4 곳을 전부 고쳐야 하고, 앱에 테스트 전용 우회 경로를 심는 것도 피하고 싶었다. 이 방식은 **401/403 판정 로직(`enforce_api_auth`)을 그대로 태운다** — 바뀌는 것은 "주체가 누구인가" 뿐이라, 권한 규칙이 깨지면 `@pytest.mark.real_auth` 테스트가 잡는다.
- **자동 분석은 "수동만" 원칙을 한 지점에서 완화한 사용자 결정이다.** 근거 두 가지를 계약 주석(`analysis/service.py` 상단)과 CLAUDE.md 에 함께 남겼다. (1) 대상이 **fingerprint 분석 이력이 전혀 없는 그룹**으로 한정된다 — 새 오류 유형이 나타난 첫 회차에만 1 회 돈다. (2) 진입점이 수동과 **같은 `create_analysis_job`** 이라 `allow_ai_analysis`·멱등(부분 유니크 인덱스)·일일 한도(429)가 그대로 비용 상한이 된다. 자동 실행에 별도 경로를 만들지 않은 것이 이 완화를 안전하게 만드는 유일한 장치다. 임계치 기반 자동 실행과 자동 재분석은 여전히 없다.
- **미분석 판정은 상태를 보지 않는다** — 실패한 분석도 "이력 있음"이다. 실패를 미분석으로 세면 같은 실패를 매 회차 자동으로 다시 태운다(반복 과금). 재시도는 사람이 누른다.
- **due 판정은 `finished_at` 이 아니라 `started_at` 기준이다.** 실패해서 `finished_at` 이 비어 있는 회차가 하나만 있어도, NULL 취급에 따라 그 정책이 영원히 due 이거나 영원히 안 도는 상태가 된다. 시작 시각은 성공·실패와 무관하게 항상 있다. 수동 실행도 같은 테이블에 남으므로 손으로 돌린 정책은 자연히 한 주기 미뤄진다(중복 조회 방지 — 의도한 동작이다).
- **`triggered_by` 는 이력·배지용이고 동작을 분기하지 않는다.** 분기가 생기는 순간 "스케줄 실행만 한도를 안 탄다" 같은 구멍이 열린다. `create_query_run` / `create_analysis_job` 은 값만 받아 저장한다.
- **겹침 방지는 in-process 락 — 단일 uvicorn 워커 전제다.** DB 어드바이저리 락으로 올리는 것은 어렵지 않지만, 지금 필요 없는 분산 조정을 미리 넣지 않았다. 위험은 이 결정이 **조용히 깨진다**는 것이다(워커를 늘려도 겉으로는 정상 동작처럼 보인다). 그래서 `scheduler/service.py` docstring · README · compose 주석 · CLAUDE.md 네 곳에 같은 문장을 박아 뒀다.
- **정책 저장 시 `schedule_enabled` 는 주기 없이 켤 수 없다(422).** 한도 값과 같은 원칙이다 — 저장은 사람이 고칠 수 있는 순간이라 기본값을 조용히 끼워 넣지 않는다. 주기 없이 켜진 정책은 화면에 "켜짐"으로 보이는데 스케줄러가 영원히 건너뛴다. PATCH 는 **병합 후 실효값**으로 검증한다 — 요청 하나만 보면 "주기만 지운" 요청이 이미 켜진 정책을 무주기로 만든다.
- **`total_errors_24h` 는 실패 시 `null` 이지 0 이 아니다.** `estimated_cost` 와 같은 규칙 — 0 은 "오류가 없었다"로 읽힌다. 정책 수만큼 Loki 호출이 나가므로 정책별로 **벽시계 타임아웃**(스레드 + `future.result(timeout=...)`)을 걸고 예외를 삼켜 경고 코드로 강등한다. 어댑터의 소켓 타임아웃만으로는 재시도·리다이렉트가 겹쳤을 때 벽시계 시간을 보장하지 못하고, 정책이 10 개면 그 누적이 첫 화면의 대기 시간이 된다. 어댑터 **생성**은 호출 스레드에서 한다 — 팩토리가 ORM 속성을 읽으므로 다른 스레드에서 만들면 세션을 스레드 밖에서 만지게 된다.
- **`summary` 는 비활성 정책도 싣는다.** 목록에서 빼면 "지웠나?"와 "비활성인가?"가 화면에서 구분되지 않는다. 대신 metric 호출은 걸지 않고 `policy_inactive` 경고를 붙인다.
- **`app.*` 로거에 핸들러를 붙였다** (`main.configure_logging`). uvicorn 은 자기 로거만 설정하고 루트는 WARNING 으로 남긴다 — 그대로 두면 스케줄러가 남기는 INFO(실행·스킵 사유)가 어디에도 보이지 않는다. "한도 초과는 예외 없이 스킵하고 로그로 남긴다"는 계약이 로그가 안 보이면 성립하지 않는다.
- **revision 0004 는 관리자 계정을 만들지 않는다** (위 시드 항목과 같은 이유). 스키마만 추가한다: `users`·`user_sessions` 테이블, `analysis_policies` 스케줄 3 필드, `query_runs`/`analysis_jobs` 의 `triggered_by`(server_default `manual` — 기존 행은 실제로 전부 수동이었으므로 백필이 "편의"가 아니라 "사실"이다).

## Phase 6 — 2차 사용 피드백 (백엔드 몫)

- **계정 목록은 GET 인데도 admin 전용이다.** 전역 규칙은 "viewer 도 GET 은 된다" 지만 사용자 이름 목록만은 예외로 `require_admin` 을 붙였다. 계정 이름 목록은 로그인 시도의 절반이고(그래서 로그인 실패 사유도 구분해 주지 않는다), viewer 가 그것을 통째로 읽을 이유는 없다. 예외를 라우터 하나에 좁게 두는 대신 전역 규칙은 건드리지 않았다 — 전역을 손대면 기본값이 다시 "열림" 쪽으로 흔들린다.
- **마지막 관리자 보호는 "활성 admin 수" 로 판정한다.** 비활성 admin 을 세면 "관리자가 또 있다"고 착각한다 — 그 계정은 로그인 자체가 막혀 있어 아무것도 되돌릴 수 없다. 판정은 라우터가 아니라 서비스(`auth.service.update_user`)에 두었다. `DELETE` 는 `active=false` 인 `PATCH` 이므로, 규칙을 라우터에 두면 두 경로가 갈라지고 한쪽만 뚫린다.
- **자기 자신 비활성은 관리자가 여럿이어도 막는다.** 마지막 관리자 규칙과 별개다 — 스스로 자기 발등을 찍는 조작이고, 되돌리려면 남의 손이 필요하다. 반대로 **자기 강등은 막지 않는다**: 관리자가 둘 이상이면 정당한 조작이고, 하나뿐이면 마지막 관리자 규칙이 이미 잡는다.
- **비활성화·비밀번호 변경은 세션 행을 지운다.** `resolve_session` 이 매 요청 계정을 다시 읽으므로 비활성 계정은 어차피 막히지만, 그것은 "판정이 막는다" 이지 "세션이 없다" 가 아니다. 비밀번호를 바꾸는 이유의 절반은 "이미 유출됐다" 인데, 회수하지 않으면 옛 쿠키가 남은 12 시간 동안 그대로 통과한다. 그래서 자기 비밀번호를 바꾸면 **자기 세션도 끊긴다** — 놀랍지만 의도다.
- **계정 삭제는 실삭제가 아니라 비활성화다** (정책·연결의 `DELETE` 와 같은 규칙). 행을 지우면 그 계정이 남긴 이력의 참조가 끊긴다. 응답은 `UserRead` 의 상위 집합(`id`·`active`·`created_at` 추가)이라 화면이 목록을 다시 받지 않고도 행을 갱신할 수 있다. 로그인·`/auth/me` 의 `UserRead` 자체는 건드리지 않았다 — 거기에 id 를 흘릴 이유가 없다.
- **검색어의 `%`·`_` 는 이스케이프한다.** 안 하면 검색창에 `%` 한 글자를 넣은 순간 전체 일치가 된다. 그리고 `q` 는 **개수 쿼리에도 같은 조인**으로 걸어야 한다 — items 에만 걸면 `total` 이 전체 건수로 남아 페이지네이션이 있지도 않은 페이지를 만든다.
- **검색용 인덱스는 새로 만들지 않았다.** 날짜 범위는 기존 `ix_analysis_jobs_requested_at` 이 그대로 받는다. `q` 는 `%term%` 부분 일치라 B-tree 로는 애초에 못 타고, 태우려면 PostgreSQL `pg_trgm` 확장 + GIN 인덱스가 필요하다. `analysis_jobs` 는 분석 1 회당 1 행이고 일일 한도(기본 50)가 상한이라 연간으로도 수만 행이다 — 확장 의존성과 마이그레이션을 지금 지불할 이유가 없다. 되짚을 기준은 "행이 수십만 개가 되거나 검색 응답이 눈에 띄게 느려질 때" 다.
- **`group_by` 를 안 주면 `buckets` 는 빈 배열이 아니라 `null` 이다.** "분해를 요청하지 않았다"와 "분해했더니 아무것도 없었다"는 다른 상태이고, 빈 배열로 합치면 화면이 "이 기간에 사용량이 없다"를 잘못 그린다. 모르는 값은 조용히 무시하지 않고 422 다 — 오타를 무시하면 화면은 빈 표를 보여주면서 이유를 말하지 못한다.
- **일별 버킷의 하루는 `app_settings.timezone` 의 로컬 날짜다** (일일 한도와 같은 규칙). 기준이 다르면 "한도 50 중 13 건 썼다"와 "오늘 13 건"이 서로 다른 날을 가리킨다. 변환은 SQL 이 아니라 Python 에서 한다 — 백엔드마다 날짜 함수·타임존 지원이 다르고, 데이터량이 작아 얻는 것이 없다. 정책 버킷은 usage → job → group → run → policy 를 **한 번의 outer join** 으로 읽는다(N+1 금지). 전부 outer 인 이유는 고리가 끊긴 기록도 `unknown` 으로 세어야 버킷 합과 `total_jobs` 가 맞기 때문이다.
- **정책별 "최신 성공 회차" 는 `max(started_at)` 이 아니라 윈도 함수다.** 같은 초에 들어간 두 회차가 있으면 max 로는 둘 다 남아 그룹이 통째로 중복된다. `row_number() over (partition by policy_id order by started_at desc, id desc)` 로 정렬 키를 실행 이력 목록과 같게 맞췄다. 겹치는 정책이 같은 오류를 잡아 **같은 fingerprint 가 여러 줄 나오는 것은 중복이 아니다** — "두 정책이 같은 오류를 보고 있다"는 사실이고, 합치면 어느 정책 화면으로 들어가야 하는지가 사라진다.
- **`series_24h` 는 새 Loki 호출이 아니라 이미 받은 응답의 재사용이다.** 따로 부르면 정책 수만큼의 호출이 두 배가 되고(첫 화면 대기 시간이 그만큼 늘어난다), 합계와 시계열이 서로 다른 순간을 가리키게 된다. metric 이 `sum by (service)` 라 한 시각에 점이 여러 개 오므로 **시각 기준으로 합쳐서** 싣는다 — 그래야 "선 아래 면적 = `total_errors_24h`" 가 성립한다. 실패 시 빈 배열인 것은 `total_errors_24h=null` 과 같은 이유다 (0 짜리 선은 "오류가 없었다"로 읽힌다).
- **DB 스키마 변경 없음.** 다섯 건 모두 기존 테이블·인덱스로 답할 수 있는 조회거나(2·3·4·5), 이미 있는 컬럼(`users.active`·`role`·`password_hash`)의 쓰기다(1). 새 revision 을 추가하지 않았다.

## Phase 6 — 2차 사용 피드백 (프론트 몫)

- **관리 영역(/admin)은 메뉴 숨김 + 라우트 가드 이중이다.** 메뉴만 숨기면 주소 직접 입력으로 뚫리고, 가드만 있으면 viewer 가 "왜 없는지 모르는 메뉴"를 헤맨다. 가드 화면은 사유와 대안 경로를 적는다.
- **`buckets: null` 과 `[]` 는 다른 상태다** — null 은 "요청이 분해를 지원하지 않음(구버전 백엔드)", 빈 배열은 "기간에 기록 없음". 화면 문구를 가른다. (백엔드가 null 키를 생략하지 않는 이유: `response_model_exclude_none` 은 `estimated_cost: null` 까지 지워 "0 이 아니라 null" 계약을 깬다.)
- **심각도 배경색은 배지 병기가 필수다** — 색만으로 구분하면 접근성이 깨지고, 미분석 행은 칠하지 않는다(회색 배경은 info 등급과 섞인다). 전용 페이지와 대시보드 패널이 같은 컴포넌트를 쓰게 해 정렬·색 규칙이 화면마다 갈리지 않게 했다.
- **토큰 차트와 비용 차트는 분리한다** — 토큰 수와 달러가 한 눈금을 쓰면 한쪽이 바닥에 눌린다. 비용 null 은 막대를 그리지 않는다(0 금지).
- **검색·필터는 서버에만 맡긴다** — 받은 페이지를 클라이언트에서 다시 거르면 total 과 페이지 수가 어긋나고 다음 페이지의 일치 항목이 영영 안 보인다.
- mock 의 auth 예외가 `/api/auth/` 접두사 전체로 열려 있어 계정 목록이 미인증에 나갈 뻔했다 — **화이트리스트는 항상 정확한 경로 열거**로 한다 (백엔드 `PUBLIC_API_PATHS` 와 같은 원칙).

## Phase 7 — 대시보드 지표 확장

발단은 문서 검증이었다: 옵시디언의 "로그 모니터링 지표와 현재 대시보드의 공백" 문서를 코드와 대조해 결함 1건(overview 시리즈가 시각별로 접히지 않아 서비스 수만큼 같은 시각이 그려짐 — 실서버 재현)과 지표 공백을 확인했고, 그중 **일일 한도 소진율 · 유입량 · 오류 비율 · 수집 중단 경고**를 구현 범위로 확정했다. 수집 지연·고유 영향 대상 수는 각각 LogQL 밖의 문제 / 그룹화 원칙과의 충돌이라 보류했다 (판단 근거는 그 문서에 있다).

- **접기 규칙과 회차 COUNT 는 `dashboard/counting.py` 한 곳이다.** 시리즈 접기 버그의 원인이 정확히 "같은 규칙의 손 복사" 였다 — summary 는 접었고 overview 는 안 접었다. 같은 규칙을 두 모듈에 두 번 쓰지 않는다. `by_service` 는 접기 **전** 포인트로 먼저 계산한다(접으면 라벨이 사라진다) — 이 순서를 테스트가 못 박는다.
- **`group_count`·`unanalyzed_group_count` 는 회차 없으면 0 이 아니라 null.** 0 은 "그룹이 없었다"로 읽히고, 그러면 "아직 한 번도 돌지 않았다"와 구분되지 않는다 (비용 null 규칙과 동일 원리).
- **분모 쿼리(`baseline_query`)는 오류 쿼리에서 역산하지 않는다 — 운영자가 명시한다.** 셀렉터를 기계적으로 벗겨 내면 대부분 조용히 다른 범위를 세고, 틀린 비율은 없느니만 못하다. 미설정이면 계산하지 않고(null), 실패는 `baseline_query_failed` 경고 하나로 강등한다(분모의 하위 경고를 올리면 오류 metric 의 같은 코드와 섞여 "무엇이 비었는지"를 구분할 수 없다). `ingest_total=0` 은 살리고 `error_ratio` 만 null — 유입 0 은 사실이다.
- **분모는 오류 metric 과 같은 provider 인스턴스·같은 range·step 으로 1회만 더 건다.** 두 번 build 하면 같은 화면의 두 숫자가 서로 다른 연결 상태를 볼 수 있다. summary(홈)에는 넣지 않았다 — 정책당 Loki 호출이 두 배가 된다.
- **수집 중단 확인은 조회 실행 경로에 얹었다** (`check_service_presence`). "언제 확인할 것인가"를 새로 정하지 않기 위해서다 — 수동·스케줄이 같은 `_execute_query_run` 을 타므로 별도 감시 루프(=새 자동 실행)가 필요 없고, 결과는 `ingest_absent` **경고 기록뿐**이다(알림·자동 실행 없음 — 자동 트리거는 `auto_analyze_new` 하나 계약 유지). 확인 실패는 `presence_check_failed` 로 강등하고 조회는 성공으로 남긴다. `supports_presence=False` 어댑터는 경고 없이 건너뛴다 — 소스가 못 하는 일은 설정의 잘못이 아니다.
- **presence 는 정책 쿼리가 아니라 라벨 셀렉터로 센다.** 정책은 보통 `level="ERROR"` 로 좁혀져 있어, 그 쿼리로는 "오류 없는 정상 서비스"와 "로그가 끊긴 서비스"가 똑같이 0 이다. 서비스 이름 이스케이프는 **두 겹**(`escape_label_value_regex`): RE2 층(`re.escape`) 위에 LogQL 문자열 층(백슬래시 증식 + `"` escape) — 한 겹만 하면 `auth.api` 같은 이름에서 쿼리 전체가 파싱 실패한다.
- **한도 게이지는 429 와 같은 계산을 보여 준다.** `GET /usage/daily-limit` 의 사용량·하루 경계는 전부 `analysis.service.daily_usage` 재사용이다(usage → analysis 는 `usage/integrations.py` 지연 import). 게이지 전용 집계를 만들면 "아직 2회 남았다"는 화면에서 429 가 나는 순간 게이지는 없느니만 못하다. 정책 목록은 **자체 한도를 가진 정책만** 싣는다 — 없는 정책까지 실으면 "정책마다 별도 상한이 있다"로 오해하게 만든다.
- **(프론트) 유입량은 오류 추이에 겹치지 않고 축을 나눴다** — 유입량이 두 자릿수 커서 한 축에서는 오류 곡선이 바닥에 눌린다. `null` 은 전부 `-` 이고 사유를 세 갈래(미설정/실패/정책 미선택)로 적는다.
- **(프론트) 수집 중단 배지의 출처는 조회 회차 경고다** — 정책 상세는 실행 결과·최근 회차·overview 세 출처를 메시지 기준으로 접고, 홈 카드는 `last_run.warnings` 를 쓴다. 배지 텍스트와 부재 서비스 이름을 항상 병기한다(색만으로 구분 금지).
- **(프론트) 로그 소스 연결 화면(당시 `/admin/loki-connections`, Phase 9 에서 `/admin/log-source-connections` 로 개명)은 이번에 신설된 화면이다** — 그전까지 Loki 연결은 정책 편집 드롭다운에서 고르기만 할 수 있었고 만들거나 고칠 자리가 없었다. `expected_services` 입력이 페이지를 만들게 했다.
- **(프론트) daily-limit 엔드포인트가 없으면 게이지를 감춘다** — `0/0` 은 "다 썼다"로 읽힌다 (`isEndpointMissing` 기존 패턴).

## Phase 8 — UI 전면 다듬기 (프론트 전용)

기능 phase 가 아니라 표현 phase 다 — API·mock·백엔드 무변경. 진행 순서는 기반(디자인 시스템·레이아웃) 1트랙 선행 → 그 트랙이 확정한 컨벤션 가이드를 페이지 3트랙에 주입. 네 범위(밀도·시각·사이드바·다크)가 같은 파일을 건드려서 전부 병렬로는 못 돌린다.

- **다크 모드는 클래스별 `dark:` 가 아니라 의미 토큰이다.** `bg-white dark:bg-slate-900` 을 클래스마다 다는 방식은 한 군데만 빠뜨려도 검은 화면에 흰 카드가 남는다. `--color-surface` 같은 역할 이름을 `@theme` 에 두고 `html.dark` **한 블록**이 값을 뒤집는다. 예외는 뜻이 색에 붙은 tone(info/warning/danger)뿐 — `ui.tsx` 의 `toneStyles` 한 곳에서만 `dark:` 짝을 맞춘다. 테마 상태는 light/dark/system 3상태(localStorage `aila-theme`), 첫 페인트 깜빡임 방지 스니펫은 `index.html` 인라인.
- **설명문 이주는 삭제가 아니다.** `count_over_time`·fingerprint·"null 은 0 이 아니다" 류 계약 문구는 본문에서 `InfoTip`(ⓘ, 키보드·터치 접근 가능)으로 옮기되 한 글자도 지우지 않았고, 같은 문장은 상수로 뽑아 여러 ⓘ 가 공유한다. **위험·비용·권한 경고는 접지 않는다** — `auto_analyze_new` 비용 경고, "연결 테스트도 실제 과금", 수집 중단의 "기록일 뿐", 429 사유는 본문 그대로다. `title=` 속성만 있던 계약 문구는 터치·키보드에서 안 뜨므로 전부 `InfoTip` 으로 승격했다.
- **위계는 "무엇을 먼저 보라"다.** 홈 카드는 큰 숫자를 하나(미분석)로 줄이고 24h 건수를 추이와 한 칸에 합쳤다(정보 무게: 수집 중단 > 미분석 > 오류 수 — 수집 중단만은 축약하지 않는다). 대시보드 지표는 6칸 동일 크기 → 핵심 3(Stat) + 보조 3(SubStat) 두 줄. 정책 폼은 4섹션으로 나누되 **비용이 나가는 스위치 셋(allow_ai_analysis·일일 한도·auto_analyze_new)을 한 카드에 모았다** — 서로를 게이트하는 값이 흩어져 있으면 그 의존이 화면에서 안 보인다.
- **스켈레톤은 뼈대를 아는 자리에만.** 열·칸 수가 고정된 표·타일에만 쓰고, 결과 개수를 모르는 목록(오류 그룹·usage 분해·미리보기)은 `LoadingBlock` 유지 — 스켈레톤이 "N건 있다"는 거짓 신호가 되기 때문이다.
- **위험 동작은 2단 확인으로 통일하되 버튼을 잠그지 않는다** (`adminConfirm.tsx`). 확인 문구는 "정말?"이 아니라 무엇이 일어나는가(세션 무효화·기존 기본 해제·서버 409 사유)를 적는다. 마지막 admin 보호 같은 규칙은 눌러서 409 를 받는 경로가 살아 있어야 실제로 도는지 확인된다. 비활성화 버튼에 휴지통 아이콘을 붙이지 않았다 — "비활성화는 삭제가 아니다"가 계약인데 그림이 반대를 말하면 안 된다.
- **사이드바와 AdminPage 탭은 당분간 공존한다.** 사이드바 관리 섹션이 `/admin` 한 줄만 노출하므로 하위 5화면의 입구는 탭이 유일하다. 사이드바가 하위 항목을 직접 싣게 되면 탭을 지워야 한다(활성 표시가 두 곳에서 갈린다) — 조건을 파일 머리주석에 남겼다.
- 남긴 것: `SubStat`·`ConfirmButton` 은 페이지 로컬이며 다른 화면이 필요로 하면 `ui.tsx` 로 승격(그때 `Button` ref 전달 추가). 정책 목록의 검색·필터는 승인 범위 밖이라 미구현. **브라우저 시각 확인은 크롬 확장 미연결로 코드·빌드 CSS 검사로 갈음했다** — 실사용에서 다크 대비·툴팁 잘림이 보이면 그게 첫 피드백 대상이다.

## Phase 9 — Loki 고정 이름 일반화

KNOWN-GAPS 에 "두 번째 어댑터 phase 에서 함께" 로 보류했던 항목을 **사용자 결정으로 앞당겼다.** 근거: 로컬 데모 전용이라 외부 API 소비자가 0 이고(별칭 없는 클린 브레이크가 가능한 유일한 시기), 미룰수록 잘못된 이름 위에 코드가 쌓인다. "추측 일반화" 우려는 입력 UI 설계에 해당하지 단순 개명에는 해당하지 않았다.

- **정본 이름 4종**: `LogSourceConnection` / `log_source_connections`(+`log_source_connection_id`) / `AnalysisPolicy.query` / `/api/log-source-connections`. revision 0006 은 rename 전용(형태·데이터 무변경)이다.
- **Loki 라는 이름이 남는 곳은 두 가지뿐이다** — 어댑터(`app/loki/`·`LokiProvider`: Loki 전용인 것이 사실이므로)와, "LogQL" 이 쿼리 언어 자체를 가리키는 문장·실제 쿼리 문자열·` ```logql ` 코드 펜스. 이 경계는 CLAUDE.md 작업 규칙에 명문화해 다음 스윕이 재판단하지 않게 했다. 제품 태그라인("Loki 기반 AI 로그 분석기")은 프로젝트 이름이라 유지 — 바꿀지는 별도 결정.
- **UI 라벨은 "쿼리 (LogQL)" 병기** — 일반 이름을 앞세우되 현재 소스의 언어 이름을 잃지 않는다. 연결 화면 제목이 "로그 소스 연결"로 일반화된 대가로 목록 행에 `source_type` 배지를 추가했다.
- 배포 순서: 개명은 구 코드↔신 스키마가 비호환이라 **backend 정지 → 0006 → 재빌드**로 불일치 창을 없앴다.

## 운영 노트

- **모델 단가표는 `PUT /api/settings/model_pricing` 로 관리한다** (사용량 화면의 인라인 등록 폼도 같은 API). 미등록 모델의 추정 비용은 `-` 로 표시된다 (0 이 아님 — 의도). 프로바이더 API 는 단가를 제공하지 않으므로 자동 수집은 불가능하다.
- **일일 분석 한도는 `app_settings.timezone` 의 로컬 자정 기준** 리셋 (기본 `Asia/Seoul`). 전역 기본 50, `PUT /api/settings/daily_analysis_limit` · `PUT /api/settings/timezone`.
- **전송 페이로드 감사는 llm-mock 연결에서만 가능** — 실 프로바이더에는 `/debug/last-request` 가 없다. 마스킹 회귀 검증은 llm-mock 으로.
- **compose 의 Fernet 키는 데모용 평문이다.** 교체하면 기존 저장 secret 복호화 불가 → 연결 재등록.
- frontend 컨테이너는 소스를 COPY 하므로 수정 후 `--build frontend` 필요.
- `scripts/e2e_demo.py` 는 실행마다 일일 한도 2건 소모. **Phase 5 부터 사전 점검 단계에서 먼저 로그인한다** (`--username/--password`, 기본 `admin/admin`). llm-mock·Loki·demo-api 는 인증 대상이 아니라 `scripts/trigger_scenarios.py` 는 손댈 것이 없었다.
- **compose 의 기본 관리자 계정은 `admin/admin` 이다** (Fernet 키와 같은 성격의 데모용 평문). 앱 기동 시 시드되며, 마이그레이션 전에 뜬 컨테이너는 시드를 건너뛰고 경고만 남기므로 `alembic upgrade head` 뒤 `restart backend` 가 필요하다.
- **스케줄러를 켠 채로 워커를 늘리지 않는다.** 늘려야 하면 `scheduler/service.py` 의 in-process 락을 DB 어드바이저리 락으로 먼저 바꾼다.
- **유입량·오류 비율은 정책의 `baseline_query`, 수집 중단 경고는 연결의 `expected_services` 를 채워야 나온다** (Phase 7). 데모 스택은 정책 #3 에 `{service=~"payment-api|order-api|auth-api"}`, 연결에 서비스 3종이 설정된 상태다. 검증 시 가짜 서비스(billing-api)로 `ingest_absent` 경고 생성·홈 카드 표시·원복 후 소거까지 실서버에서 재현했다.

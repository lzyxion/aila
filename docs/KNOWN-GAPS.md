# 의도적 공백 (Known Gaps)

**안 만든 것과 못 만든 것을 구분하는 문서다.** 여기 있는 항목은 전부 이유를 알고 보류한 것이며, 각 항목에 "다시 볼 조건"이 붙어 있다 — 조건이 충족되기 전에 구현하는 것은 이 문서의 이유를 반박하고 나서다. 버그·미해결 결함 목록이 아니다 (그건 발견 즉시 고친다).

관련 문서: 결정의 배경은 `DECISIONS.md`.

## 1. 지표 공백 (Phase 7 검증에서 확인, 의도적 보류)

| 공백 | 보류 이유 | 다시 볼 조건 |
| --- | --- | --- |
| 신규 fingerprint·급증률 (회차 간 비교) | `error_groups` 가 `query_run_id` 에 종속 — 그룹은 조회 1회 안에서만 유효하고 회차 간 조인 경로가 없다. fingerprint 상위 엔티티 또는 회차 간 집계 뷰 = **스키마 변경**이 따라온다 | 스케줄 실측으로 회차가 정기적으로 쌓인 뒤 (비교할 회차가 있어야 비교 지표가 의미를 갖는다) |
| `dropped_count` 파싱 실패분 분리 | 컬럼에 제외 정규식분과 합산 저장된다. 회차별로는 `parse_error` 경고의 `count` 로 파싱 실패 단독 건수를 알 수 있어 급하지 않다 | 파싱 실패를 **집계 가능한 지표**(추이·비율)로 봐야 할 때 — 컬럼 분리 + 새 revision |
| 분석 실패율(%) · p95 지연 | 현재는 실패 건수·평균 지연만. 분석량이 일 수십 건 규모라 백분위가 통계적 의미를 갖지 못한다 | 분석량이 일 수백 건 이상으로 늘거나, 프로바이더 장애/스키마 실패를 분리 추적할 필요가 생길 때 |
| 수집 지연 (ingest lag) | LogQL 로 구할 수 없다 — 쿼리 결과에 "Loki 가 받은 시각"이 없다. 수집기(Alloy)의 Prometheus 지표가 필요하며, 이는 LogSourceProvider 추상화 밖의 새 데이터 소스 계층이다 | 제품 요구로 승격되면. 그 전까지는 검증용 Grafana(`infra/grafana/dashboards/aila-ingest.json`)의 몫 |
| 고유 영향 대상 수 (영향받은 사용자·요청 수) | 그룹화 원칙과 정면 충돌 — 같은 오류를 묶으려고 `request_id`·사용자 ID 를 플레이스홀더로 지우는데, 영향 범위는 정확히 그 지워진 값들의 고유 개수다. 세려면 그룹화 이전 단계나 LogQL 쪽에 새 파이프라인 단계가 필요하다 | 마스킹·그룹화 순서를 건드리지 않는 설계가 나올 때만 (마스킹 약화는 금지) |
| 유입량·오류 비율의 홈(summary) 표시 | 정책 상세(overview)에만 있다. summary 에 넣으면 정책 수만큼 Loki 호출이 **2배** | 홈 카드에서 비율이 실제로 필요해지고 호출 비용을 감수하기로 결정할 때 |

## 2. 자동화 경계 (계약 — 완화가 아니라 위반이 되는 선)

| 없음 | 이유 | 다시 볼 조건 |
| --- | --- | --- |
| 임계치 기반 자동 분석·자동 재분석·알림 연동 | 자동 트리거는 정책의 `auto_analyze_new` 하나뿐 (README 계약상 제약). 비용이 오류 **발생량**에 비례하게 되는 순간, 오류 폭증 = LLM 요금 폭증이 된다 | 스케줄 관찰 운전의 비용·빈도 데이터가 쌓여 상한을 근거 있게 정할 수 있을 때 (설계 caution 의 조건 그대로) |
| 수집 중단(`ingest_absent`) 알림·자동 대응 | 경고 **기록**까지가 계약 안이다. 알림을 붙이는 것이 정확히 위 규칙이 막는 일 | 위와 동일 — 자동화 확대 논의에 포함해서만 |

## 3. 아키텍처 유보

| 유보 | 이유 | 다시 볼 조건 |
| --- | --- | --- |
| 스케줄러 in-process 락 (단일 uvicorn 워커 전제) | 지금 필요 없는 분산 조정을 미리 넣지 않았다. **워커를 늘리면 조용히 깨진다** (같은 정책 중복 실행, 겉은 정상) | 워커를 늘리기 **전에** DB 어드바이저리 락으로 교체 — 순서가 반대가 되면 안 된다 |
| BackgroundTasks 실행 (Redis 워커 아님) | 분석은 단발 호출이고 동시성이 낮다. 태스크가 engine 만 물려받아 새 세션을 여는 구조라 워커 전환 시에도 코드 형태가 유지된다 | 분석 동시성이 프로세스 하나로 부족해질 때 (설계 "향후 확장") |
| 추가 LogSourceProvider (Elasticsearch·CloudWatch 등) | MVP 는 Loki 하나. 어댑터 경계(capability 플래그·`label_mapping`·소스 고유 문법 그대로 저장)는 이미 만들어져 있고, **이름도 Phase 9(0006)에서 일반화됐다** — 남은 것은 어댑터 구현과 소스별 입력 UI 뿐 | 두 번째 소스 요구가 실제로 올 때 |

## 4. 성능 유보 (규모 조건부)

| 유보 | 이유 | 다시 볼 조건 |
| --- | --- | --- |
| `analysis_jobs` 검색의 pg_trgm+GIN 인덱스 | `%term%` 부분 일치는 B-tree 를 못 탄다. 행이 연 수만 규모(일일 한도 50 상한)라 확장 의존성을 지불할 이유가 없다 | 행 수십만 대 또는 검색 응답이 눈에 띄게 느려질 때 — 새 revision 으로 |
| 한도 게이지의 정책별 N+1 | 정책별 사용량을 `daily_usage()` 재호출로 구한다. 전용 집계 쿼리는 "429 와 같은 계산" 보장을 깨뜨린다 | 자체 한도 정책이 수십 개가 될 때 — 그때도 같은 함수를 배치화하는 방향으로 |
| usage 집계의 Python 변환 (SQL 날짜 함수 미사용) | 백엔드(PostgreSQL/SQLite)마다 타임존·날짜 함수가 달라 이식성이 깨진다. 데이터가 작아 얻는 것이 없다 | usage 레코드가 커져 집계가 느려질 때 — PostgreSQL 전용 SQL 로 |

## 5. UI 유보 (소소한 것)

- `presence_check_failed`·`baseline_query_failed` 는 전용 UI 없이 일반 경고 목록에 라벨로만 표시 — 사용자의 다음 행동이 "설정 수정"이 아니라 "사유 확인"이라서.
- `QueryRunPage`(조회 회차 화면)에 수집 중단 전용 배지 없음 — 경고 목록에 표시는 된다. 필요 시 `IngestAbsentBadge` 재사용.
- 모델 단가 자동 수집 없음 — 프로바이더 API 가 단가를 제공하지 않는다. `PUT /api/settings/model_pricing` 수동 관리가 유일한 방법이다.

## 6. 보안 — 로컬·데모 전용 기본값 (공백이 아니라 **전제**)

외부 노출 전 필수 변경: `AILA_ADMIN_PASSWORD`(기본 admin/admin) · `AILA_SESSION_COOKIE_SECURE`(기본 false) · compose 의 평문 Fernet 키(교체 시 기존 저장 secret 복호화 불가 → 연결 재등록). 이건 "나중에 하면 좋은 것"이 아니라 노출 전 차단 조건이다.
